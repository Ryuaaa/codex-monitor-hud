# Windows 复用边界与功能对照

审计基线：已冻结的 macOS 1.0 候选提交 `864ddea`。Windows 开发仅修改 `windows/`，没有改动 macOS 的 `overlay/`、构建脚本或发布产物。

## 技术边界

macOS 版的界面、平台采集和部分产品逻辑使用 Objective-C、Foundation 与 AppKit，不能直接在 Windows 编译。Windows 版复用已经验证过的信息架构、协议方法、刷新策略、计算口径和固定样例，并用 Win32/C++17 重建平台实现。

| macOS 部分 | Windows 当前处理方式 |
| --- | --- |
| 窗口、卡片、设置和模块排序 | 用 Win32 原生控件重建三页与十五个模块；主页和所属页分别控制显隐，支持置顶、任务栏最小化、拖动、自由缩放、纵向滚动、单实例和每显示器 DPI。 |
| CPU、内存、进程树、网络、磁盘、提交量和页面文件 | 用 Windows 系统接口重写；CPU、内存、网络和磁盘使用同一个 5 秒快采，提交量、页面文件和排行使用 20 秒慢采，串行后台执行并按页面/模块需求停采。 |
| Codex 账户、额度、用量和任务列表 | 用安全子进程与管道实现官方 `codex app-server --stdio`；只保留最小只读字段，按需启动并可取消。 |
| 当前任务活动（本机推测） | 用独立轻量线程移植 macOS 的安全口径；只在卡片可见时检查近期普通 JSONL 的尾部，活跃 5 秒、空闲 20 秒，压缩或不可读时降级而不误报。 |
| Token 日汇总 | 复用“缺失不等于零”的口径，用独立 C++ 日历算法计算今日或最近日期、近 7 日和近 30 日。 |
| Token 成本与预测历史 | 已用官方每日 Token 汇总作为总量、本机会话模型样本作为价格结构，显示近 30 天费用和月度预测；增量游标与冻结费用保存为 8 MiB 上限的版本化白名单缓存，损坏时回退到有界扫描。 |
| OpenAI 服务状态 | 已用 WinHTTP 和 Windows.Data.Json 实现；只在模块实际可见时按低频节奏读取官方公共状态。 |
| 周额度消耗提醒 | 已接入共用额度历史；默认关闭，支持 5–100% 阈值、滚动 24 小时/本地自然日、单周期防重复和周额度重置换周期。Windows Shell 通知不抢前台，状态原子保存成功后才发送。 |
| 自动更新 | 已实现每日/手动检查和真实安装按钮；按钮只接受新鲜完整发布信息，并在后台依次下载校验文件和 MSI、启动已验证临时助手，助手就绪后才关闭当前 HUD。准备新更新前只清理严格随机命名、非重解析且超过七天的旧目录，并保留最新两个；失败不阻断更新。仍需配置正式发布者证书指纹并完成签名发布验收。 |
| macOS 签名、公证和安装 | 不可复用；Windows 需要安装包、Authenticode 代码签名、可信时间戳和独立更新流程。 |

## Codex 只读接口边界

Windows 当前每次刷新启动一个短生命周期 `codex.exe app-server --stdio`，先发送 `initialize` 和 `initialized`，再调用：

- `account/rateLimits/read`：五小时与每周额度；
- `account/read`：订阅类型；
- `account/usage/read`：官方每日 Token 汇总；
- `thread/list`：最近任务历史。

界面会保留上次成功值，并把单方法失败与其他方法隔离。成功后 5 分钟刷新；连续失败按 1、2、5、10、15 分钟退避并封顶，下一次成功后恢复 5 分钟正常刷新。提醒关闭时，最小化或没有可见 Codex 模块会取消在途读取并暂停；用户开启周额度提醒后只保留同一条 5 分钟额度刷新，不增加轮询。

任务状态有一个不可消除的语义限制：新启动的 `app-server` 只能提供它自身进程范围内的状态，不能证明 Codex 桌面版所有任务的全局实时状态。因此 Windows 版只把 `thread/list` 作为最近任务历史；另一个“当前任务活动”模块只根据本机会话文件的近期开始/完成事件做趋势推测，显示可确认的活跃数量和最长时长，但不冒充官方精确状态。

为保护隐私，保留的数据模型不包含邮箱、任务标识、预览、工作目录、会话路径、提示词、回复或工具内容；原始 JSON-RPC 行和标准错误不会进入 UI 或落盘。

## 安全与资源边界

- `codex.exe` 必须是安全的绝对普通文件；自动查找限定固定目录、层数和候选数量。
- 不经命令行外壳启动；子进程只继承指定管道，并在运行前加入“关闭即清理”的 Windows Job。
- 单次接口读取有行大小、队列、总输出、标准错误和 15 秒总时限；响应洪水、卡死、取消和退出都必须回收进程树。
- 性能、Codex 账户和本机任务活动各自只有一个按需串行后台工作线程；窗口消息只接收已裁剪结果，不携带拥有所有权的裸指针。
- 设置仅保存白名单字段，并通过同目录临时文件替换，避免半写入状态。
- 更新助手不通过进程编号重新打开旧程序，而是消费启动方显式继承的进程句柄，并同时核对编号、创建时间和程序路径；等待失败不会进入 Windows Installer。
- MSI 安装失败时，只会在旧 EXE 仍通过固定发布者和精确旧版本校验后恢复启动；安装成功后仍要在锁住路径的情况下验证新 EXE 的 Authenticode、固定发布者、产品名、原文件名和版本，再直接调用 `CreateProcessW`。助手自身不删除程序文件。

## CI 与测试证据

Windows x64 CI 当前负责：

1. 运行源码契约检查；
2. 使用安装的 MSVC 配置并编译 Release；
3. 运行全部便携算法测试和 Windows 原生集成测试；
4. 验证并上传原始 `CodexMonitorHUD.exe`；
5. 生成、解包复核并上传便携 ZIP 与 SHA-256 校验文件；
6. 构建未签名 MSI，真实执行安装/卸载测试后上传 MSI 与 SHA-256。

新增测试覆盖十五个模块设置迁移、网络/磁盘四项速度的首帧/重置/不可用与固定格式、保守诊断口径、Codex 与服务状态 JSON 解析、安全进程启动与发现、官方握手和四个只读方法、乱序/异常/洪水响应、方法级旧值保留、Token 日期数学、额度趋势与白名单历史、周额度提醒的默认关闭/阈值/模式/数据不足抑制/周重置换周期/单周期防重复/保存先于通知/失败恢复、本机会话活动的字段隔离、120 秒/64 文件/1 MiB 边界、压缩降级、5 秒/20 秒节奏与暂停失效、本机会话费用混合口径、后台恢复和无遗留子进程，以及一键更新的固定下载顺序、失败短路、取消回收、更新助手退出等待、安装后 EXE 身份和未验证文件不启动。

这些证据可以证明源码契约、Windows x64 编译和固定输入行为，但不能替代真实用户机器上的交互、视觉、资源占用、账号数据和任务管理器对照。

## 下一阶段建议顺序

1. 先完成真实 Windows x64 交互验收：图标、三页、十五个模块开关、滚动、自由缩放、置顶、最小化、DPI、多显示器和设置恢复。
2. 用真实已登录 Codex 对照五小时/每周额度、订阅、Token 日期与汇总、最近任务历史和本机任务活动趋势，并核验主流安装渠道的 `codex.exe` 自动发现。
3. 对照任务管理器和资源监视器校准性能数据（包括下载/上传和磁盘读/写），并记录空闲、可见、最小化三种状态的资源占用。
4. 再补性能历史；网络/磁盘实时速度、额度通知、Token 成本/预测与服务状态第一版已完成。
5. 在真实 Windows x64 验收等比拖拽、动态文字高度、像素滚动、透明度和锁定手感，并为现有更新器、安装包配置 Authenticode 证书和可信时间戳后，再做正式发布验收。
6. x64 稳定后单独建立 ARM64 构建、CI 和真实设备验证，不把“工具链可能编译”当作已支持。
